# LNG carriers page: text, clarity and parity audit (2026-11-05)

Scope: the LNG tracker page as built on 2026-11-05 (`lng-carriers-researcher/work/lng_review_lng-review_20261105_1646_ET.html`, 18 batch dirs), read against the GOGPT page (`gogpt-researcher/work/gogpt_review_germany_20261008_1314_ET.html`) and the pipelines page (`pipelines-researcher/work/review_static/gas-batch.html`). Each page was loaded in Chrome through Playwright; the header, filters, queue, the first four cards (closed and with every details block open), the suggest form, the how-to and keyboard dialogs and every tooltip were screenshotted and dumped as text. Code anchors are in `trackers/lng/web/ext.js` unless another file is named. The brief: everything should read clearly, with no extraneous text or formatting, and look like the GOGPT and pipelines pages except where LNG genuinely differs.

Severity: P1 reads wrong or contradicts itself; P2 extraneous or inconsistent with the other trackers; P3 polish. Each finding has a checkbox so the list can be worked top to bottom. All 21 were applied on 2026-11-06 (gem-review-app and lng-carriers-researcher, branch `baird`); the notes in brackets after a finding say where the fix differs from the proposal.

## P1: wrong or self-contradicting text

- [x] **L1. The how-to dialog describes GOGPT's workflow, not LNG's.** The LNG extension defines no `info`, so the core's generic text shows (`review_core/web/app.js:1361` `infoHtml`). Observed: "accept: yes, this edit goes into the actions workbook", "When the batch is built, every accepted change goes into the actions workbook. Someone then applies it by hand", "Items tab: questions and other notes the researcher raised", "Click download decisions in the top bar when you are done (or any time) and send the file back". LNG has no actions workbook, no items tab (the card is flat), and its accepts reach the sheet through push changes on the loopback server, or through `import_log.py` from the artifact page. Pipelines writes its own (`trackers/pipelines/web/ext.js:724` `info(savedWhere)`), and that is the model: what a card is (one vessel, its live sheet row), the four calls, what an accept leads to (push changes lists every cell and writes on one confirmation; on the artifact page the calls are saved and imported later), what sync backend does, what the chips mean (in the backend, already applied, cosmetic, appends, only source: IGU), what suggest records (value or cosmetic, refs gated at push time), and the item calls. Same length and register as the pipelines text, lowercase headings like GOGPT's.
- [x] **L2. The keyboard dialog is the core default and three rows are wrong for LNG.** No `help` is defined, so `app.js:1341` rows show. "i: switch the card between changes and items" does nothing useful on a flat card. "s: suggest a different value: an inline form on the change (value + note; enter saves, esc cancels)": the LNG form has textareas, where Enter is a new line and Cmd/Ctrl+Enter saves (`app.js:1298`). "d: show / hide the change's notes": the LNG block is titled "details". Pipelines edits the rows (`trackers/pipelines/web/ext.js:718` `HELP`); do the same.
- [x] **L3. The WHY box says a line is confirmed when its links were never checked.** `sureSentence` (lines 220 to 226) is driven by the tier alone. Row 76, Shipowner country/area, carries the chips "derived" and three "unchecked" links, and the box reads "We are confident (green): a live page states this value for this vessel." A derived value from `data/shipowner_facts.csv` has no live page behind it. If a confidence sentence stays at all (see L6), it has to come from the recorded verdicts, and a derived line needs its own wording.
- [x] **L4. The batch filter is hidden in code but shown on the page, and the push dialog depends on it.** Line 62 sets `hidden` on the `#f-dir` label; `review_core/web/style.css:66` (`.filters label { display: flex }`) overrides the attribute, so the batch select is on the page (screenshot `lng_filters.png` shows "batch: any"). Line 363 then tells the reviewer to "Pick a batch in the batch filter first to push one batch at a time", and the README (`lng-carriers-researcher/review_app/README.md:127`) documents push by batch. The same trap caught `#issues-link`, which got an `ext.css` rule. Decide one way: keep the filter (GOGPT and pipelines keep theirs, and the push scoping needs it) and delete lines 61 and 62 and their comment, or hide it properly in `ext.css` and drop the batch scoping from the push dialog and the README. Recommendation: keep it.
- [x] **L5. A Name change is listed as "fill a blank".** The kind filter shows "fill a blank (290)", "ref (0)", "new row (5)", and the 295 undecided lines include value changes such as row 66 Name "BW Boston" to "Marigold LNG" and row 55 Status "active" to "scrapped". `review_data.py` gives every value line kind `fill`, and the core's `KIND_LABEL` (`app.js:77`) prints it as "fill a blank". The pair table already tags each row fill, change or clear, so the data is there: set the kind from it (`change` when the cell is non-blank, `delete` when the proposal is blank, as GOGPT does) so the filter and the how-to dialog can say what a line does. Also "ref" has no label in the LNG `KIND_LABEL` (line 283 labels item kinds only), so the raw key shows; the pipelines `KIND_LABEL` has one.
- [x] **L6. The suggest form says the opposite of the pair rule.** Line 267 prints "Linked: Other names is not reviewed. Decide the partner yourself." on a strict Name / Other names pair. The core's linked dialog says "These two are decided together", and the README says the answer for this pair "is both or neither". Either the suggestion asks about the partner the way the buttons do, or the sentence states plainly what happens: "Its Other names line stays open. This suggestion does not decide it."
- [x] **L7. Reviewer-facing text carries repo jargon.** The grade reasons come from `lng-carriers-researcher/scripts/confidence.py:187` and `:196` and reach the WHY box and the "grade:" detail unchanged: "a live page states the value (§3.8c) and the value is specific to this cell", "no ref survived the §3.8c gate", "RF §4.18: a delivery roll-forward wants a source besides the vessel database", "DF §5a: the source states the order total". Researcher notes add "Rob's call: Hold (Yellow)", "research (confirms_sfoc)", "Other names += 'BW Boston' (RF §4.16)", "Decided with its Name line (RF §4.16)", source lines as "source: Tradingpedia 2026-06-09 — title <url>;" with em-dashes, and "'LNGT Americas' -> 'KLNGTP Americas'" arrows. The notes rule (user CLAUDE.md, gogpt `docs/reference/notes_style.md`) bans all of this in text written for a person. Fix at the source for new batches: plain reasons in `confidence.py` (the SOP section can stay in a code comment), and notes without section numbers, "Rob's call" prefixes or "+=" shorthand. For the legacy batches, `review_data.split_note` can drop the "Rob's call: …" line (it is the pre-fill, already a chip) and the "source: … <url>;" lines (they are the refs, already in the ref row).

## P2: extraneous text, duplication, and parity with GOGPT and pipelines

## Things that are fine

- The pair table (now / proposed, fill / change / add tags, highlighted proposed text, copy buttons) is the GOGPT table and reads the same.
- The new-row table shares the core's `sourcesTable` and verdict marks, as the README rule asks.
- The ✓ / ✗ marks and their "link checks:" tooltips are the shared `vmark` text, with the raw verdict appended; "page read" for a URL-log verdict is a sensible LNG-only state.
- The queue row (name, row · builder, N to decide, tier dots) and the card context line (tier summary, IMO, builder, owner, hull, status, delivery year) are short and all clickable filters.
- The flag chips "in the backend", "value in the backend", "already applied", "appends", "only source: IGU" are short and each tooltip is one clause.
- The sync and push dialogs: the plan table (row / vessel / column / now / will be), "write N cells", the "not pushed" list, and the "N more from batches already applied" details are clear. "synced: N lines now in the backend, M items settled" is a good toast.
- The header hides sync, push, progress and record issues on the static page, as pipelines does.
- "items with no vessel" as one card, and "settled in the backend" on a resolved item.
